# Argyle Labs

Local-first homelab & developer tooling, built around **[orca](https://github.com/argyle-labs/orca)** — a composable tool for unified communication over REST, MCP, and CLI that manages a fleet of machines from a single pane of glass, with capabilities (services, storage, containers, models, agents, and more) shipped as composable **orca plugins**.

## orca

[**orca**](https://github.com/argyle-labs/orca) — the core. One Rust binary per host that exposes a single tool surface across CLI, TUI, REST, and MCP to manage a fleet of machines from a single pane of glass. It owns the domain model (containers, storage, namespaces, pods, notifications, models, agents) and its functionality is augmented by composable, out-of-process plugins (dynamic subprocess model). The web UI is itself a plugin (peacock). Local models run by default; Claude is escalation-only.

Every plugin registers with orca through one generic surface — `service.*` (`list`, `deploy`, `backup`, `restore`, `configure`, `status`) — with rich, plugin-specific data returned in the typed `service.status` payload. Each repo below is also a **standalone setup guide**: you can deploy and operate the underlying service by hand, without orca.

## Developing a plugin

Each plugin is its own repo: an out-of-process subprocess whose only orca dependency is `plugin-toolkit`, declaring its index metadata in `Cargo.toml` (`description` + `[package.metadata.orca].category`). See the [orca plugin authoring guide](https://github.com/argyle-labs/orca/blob/main/docs/plugin-authoring.md), and [docker](https://github.com/argyle-labs/docker) or [unraid](https://github.com/argyle-labs/unraid) as worked references.

Release binaries are signed with minisign (`<asset>.minisig`, trusted comment `plugin=<name> version=<version> sha256=<hex>`); the public key is [`keys/plugin-release.pub`](keys/plugin-release.pub). To rotate: add the new key, sign with both during the overlap, then remove the old one.

## CI building blocks

Plugin repos compose their `.github/workflows/ci.yml` from **job actions**: one composite action per CI job under [`.github/actions/`](.github/actions) (`job-*`), each holding the whole job's steps from checkout to `ci-summary`, built from the tool actions beside it. A repo's `ci.yml` lists its jobs in order (build, test, lint), each with `runs-on`, the `ci-rust` `container:` and a single `uses:` step with `with:` inputs; it carries no step logic, so a fix to a job action reaches every repo. Something a repo needs that no job action does becomes a new one. They are composite actions rather than reusable workflows because Gitea runs a reusable workflow's inner job as a separate job: every check posted twice (`CI / build` and `rust build / build`) and the runner queue carried double the jobs. orca, whose scoped workspace does not fit the job actions, composes the tool actions directly in its own jobs.

Start from a template:

| Repo type | Template |
|---|---|
| Rust-only plugin | [`templates/plugin-ci-rust.yml`](templates/plugin-ci-rust.yml) |
| Plugin crate embedding a Vite frontend (`ui/`) | [`templates/plugin-ci-rust-ui.yml`](templates/plugin-ci-rust-ui.yml) |
| Scoped workspace plus an npm workspace (orca) | [`templates/orca-ci.example.yml`](templates/orca-ci.example.yml) |

### Selecting the actions version and server

`uses:` cannot take expressions, so workflows check out this repo and call the actions by path. Two Actions variables choose what is checked out:

| Variable | Effect | Unset |
|---|---|---|
| `CI_ACTIONS_REF` | Ref of `argyle-labs/.github` to run (`v1`, `v1.2.0`, a branch) | `v1` |
| `GIT_SERVER_URL` | Git server to check it out from | the server running the workflow |

GitHub leaves both unset; the Gitea org sets `GIT_SERVER_URL` to the Gitea URL and `CI_ACTIONS_REF` to the chosen version. A `vX.Y.Z` tag push moves `vX` to it ([`actions-major-tag.yml`](.github/workflows/actions-major-tag.yml)).

```yaml
- uses: actions/checkout@v4
  with:
    repository: argyle-labs/.github
    ref: ${{ vars.CI_ACTIONS_REF || 'v1' }}
    github-server-url: ${{ vars.GIT_SERVER_URL || github.server_url }}
    path: .ci
- uses: ./.ci/.github/actions/job-release-version
```

[`ci-actions-checkout`](.github/actions/ci-actions-checkout) wraps that checkout. It must itself be pulled by remote ref, since a local action cannot run before its repo is on disk; only the wrapper comes from that ref, everything under `.ci` follows the variables. Composites cannot read `vars`, so pass them:

```yaml
- uses: argyle-labs/.github/.github/actions/ci-actions-checkout@v1
  with:
    ref: ${{ vars.CI_ACTIONS_REF }}
    server-url: ${{ vars.GIT_SERVER_URL }}
```

| `job-rust-build` | `build` | `cargo-build`: every test binary, once, coverage-instrumented, into the nextest archive | `ui`, `packages`, `build-jobs`, `debuginfo`, `sccache-*` |

| `job-rust-coverage` | `test` (`needs: build`), in place of `job-rust-test` | `cargo-llvm-cov` alone on the archive: results plus lcov artifact and summary table, no `cargo-test` wrapper; compiles nothing | `image-tag`, `workflow-file`, `ui`, `build-jobs`, `debuginfo`, `sccache-*` |
| `job-vite-test` | `test-ui` | `vitest`, `svelte-check` | `working-directory`, `sccache-*` |

| `job-rust-doctest` | `lint-doctest` | `cargo test --doc` | as `job-rust-build` |
| `job-shell-lint` | `lint-shell` (host docker, no `container:`) | `bash -n`, then shellcheck from `koalaman/shellcheck:v0.9.0` | `files`, `working-directory` |

`image-tag` (default `1.95.0`) and `workflow-file` (default `.github/workflows/ci.yml`) feed the source hash; set them when a repo's `container:` tag or workflow path differs. `ui: 'true'` hashes `ui/` and places the `vite-dist` artifact, so that job `needs: build-ui`. `packages` (default `--workspace`) selects cargo packages; the actions add `--all-features`. Composites cannot read `secrets` or `vars`, so each job passes `sccache-endpoint` / `sccache-access-key` / `sccache-secret-key` from `vars.SCCACHE_ENDPOINT` and `secrets.SCCACHE_S3_*`. A `workflow_dispatch` input named `force` bypasses the pass cache. Nested actions are pulled `@main`, so a job action pinned to a branch still runs `main`'s tool actions.

### Required checks: `CI / build*`, `CI / test*`, `CI / lint*`

Branch protection requires the globs `CI / build*`, `CI / test*` and `CI / lint*`, so every job id starts with one of those words. There are no aggregate jobs and no separate coverage job: the jobs ARE the checks. Jobs run in parallel; one needs another only when it consumes its artifact. `lint` and `lint-doctest` never wait on `build`: in UI repos they need only `build-ui`.

### What each job compiles

| Job | Compiles | Reuses |
|---|---|---|
| `build` | every test binary, once, coverage-instrumented, into the nextest archive | |
| `test` | nothing | the nextest archive: tests run once from it under `cargo llvm-cov nextest` |
| `lint` | clippy's check build (`--all-targets`, sccache-backed); fmt and lock-check compile nothing | |
| `lint-doctest` | doctests (`cargo test --doc`, uninstrumented, sccache-backed) | |

Two compiles duplicate `build`'s work, both off the `build` -> `test` path: doctests, which nextest cannot run so rustdoc builds them uninstrumented, and clippy's check build, whose check-mode output cannot reuse a plain build's `target/`. Both rely on the shared sccache. Test failures fail `test`; a coverage-reporting failure only warns. `cargo-test` runs doctests too unless `doctests: 'false'`; the job actions and orca pass `'false'` and run them in `lint-doctest` / `lint`.

Each job declares the `ci-rust` `container:` with `credentials:` from `secrets.CI_REGISTRY_USER` / `secrets.CI_REGISTRY_TOKEN`; each job action starts with `actions/checkout`. Tool steps after the first in a job run `if: ${{ !cancelled() }}` so each tool reports even when an earlier one fails; the job still fails. A step that depends on an earlier one is gated on it instead: `job-rust-lint`'s clippy, lock check and actionlint run only when `rust-setup` succeeded, and `job-vite-test`'s svelte-check (which reuses vitest's `npm ci`) only when vitest succeeded. Each job ends with `ci-summary` (phase timings, sccache stats). Every step has a `name:` naming the tool, inside each composite `action.yml` too.

### Pass cache: skipping unchanged source

CI-only and doc-only changes do not rebuild or retest. `build`, `test`, `test-ui`, `lint` and `lint-doctest` each run `source-hash` after checkout, then `ci-pass-cache` in `check` mode; on a hit, a `Reuse unchanged pass` step writes "Unchanged source — reusing pass from <sha>" to the log and step summary, and every heavy step is skipped (`if: steps.pass.outputs.hit != 'true'`). On success a `Record pass` step writes the marker. Each job passes its own action name as `source-hash`'s `actions` input, so only the shared actions that job reaches are hashed; an unrelated `.github` change keeps the pass. `lint` also hashes the repo's `.github` and keys its marker by lock-check mode. `lint-doctest` skips `cargo test --doc` when no selected library target has a fenced code block in a doc comment.

The hash covers `git ls-files -s` blob ids (no file contents are read) of: tracked `*.rs`, every `Cargo.toml` and `Cargo.lock`, `build.rs`, `rust-toolchain*`, `.cargo/config.toml`, everything under any `tests/` directory, the directory of each literal `include_str!`/`include_bytes!` target (resolved against the including file) and each rust-embed `#[folder = "..."]` (resolved against the crate dir), with a leading `$CARGO_MANIFEST_DIR` taken as the crate dir and `//` comment lines skipped, plus the `image` input (the ci-rust tag) and `rustc -vV`. Paths the scan cannot see (non-literal include paths, frontend sources, fixtures elsewhere) go in `extra-paths`: the UI template passes `ui`. The calling workflow file's blob is hashed too (the `workflow-file` input, repo-root relative; the templates pass `.github/workflows/ci.yml`; else the path from `GITHUB_WORKFLOW_REF`), so changing build flags or steps invalidates every pass. The content of `.github/actions/` and `.github/workflows/` in the checkout of this repo that the action runs from is hashed as well. Nested actions are pulled `@main`, so that content matches what runs only when the caller pins every `argyle-labs/.github` action to the same ref (the templates use `@main` throughout). A pilot that pins a job action to a branch must run with `force: true`: the hashed action content comes from `@main`, so a branch run would record a pass against `main`'s hash for unmerged action changes. An unresolvable workflow file, an `extra-paths` entry matching no tracked file, a literal include or folder target outside `working-directory` or with no tracked files, or an include path using any other `$VAR` or `env!()` (use `extra-paths`) fails the step.

Markers live at `s3://<sccache bucket>/ci-pass/<repo>/<job>/<hash>` on the sccache S3 cache (same endpoint and keys as `rust-setup`), written with `curl --aws-sigv4`; the body is the commit sha that passed.

Rule: `test` skips when its own marker exists. `build` skips only when BOTH the `build` and `test` markers exist, so whenever `test` misses, `build` has run and uploaded the nextest archive it needs. UI repos keep `vite-build` running on a hit because `lint` consumes `vite-dist`.

Force a full run with `workflow_dispatch` and `force: true` (the templates declare the input); scheduled runs always pass `force: true`. Only orca has a nightly schedule; plugin repos run on push and PR only. Any cache backend failure (no endpoint/keys, network error, non-200/404 reply) is a miss with a warning, so an S3 cache outage means a full run, never a false pass; a failed record only warns.

### Per-crate pass cache: multi-crate workspaces

A plugin is one crate, so the whole-repo `source-hash` above is the right granularity for the plugin templates. A multi-crate workspace (orca) instead builds and tests only the crates whose inputs changed since a recorded pass: `build` and `test` run `crate-hashes`, then `ci-pass-cache` in `check-batch` mode, then a `Select crates to build` / `Select crates to test` step that intersects the misses with the `changes` selection (on PRs; `--workspace` keeps every miss) and passes the result to cargo as `-p` args. An empty list prints "All affected crates unchanged — reusing passes" and skips the heavy steps. On success `record-batch` writes a marker for each crate that ran.

A crate's hash is sha256 over: the `git ls-files -s` blob ids of its own directory (minus any member nested inside it), the own-file hashes of every workspace crate in its dependency closure (normal, dev and build deps, from `cargo metadata`), and the workspace-wide inputs: the `Cargo.lock` blob, root `Cargo.toml`, `rust-toolchain*`, `.cargo/config.toml`, the calling workflow file, this repo's actions and workflows (same pinning caveat as above), the `image` input and `rustc -vV`. The closure comes from `cargo metadata --all-features`, so optional workspace deps count. Dependency hashes propagate because a crate's build and test result depends on the code of everything it links: change a leaf and that leaf plus every crate that depends on it, directly or transitively, gets a new hash, and nothing else does. The closure (rather than a recursive hash of hashes) keeps dev-dependency cycles finite. Literal `include_str!`/`include_bytes!`/`#[folder = "..."]` targets outside a crate's directory are added to that crate's own files automatically (a leading `$CARGO_MANIFEST_DIR` means the crate dir; `//` comment lines are skipped; a target with no tracked files, or any other `$VAR` or `env!()` in the path, fails the step). Other files outside a crate's directory that it reads (non-literal include paths) go in `extra-paths`, one `crate: path [path...]` per line; they count as that crate's own files, so its dependents inherit them. `*: path` adds a path to every crate. A malformed line (no `:`, an empty crate name, or no paths), an unknown crate, a path matching no tracked file, or an unresolvable workflow file fails the step; orca's `files` crate picks up `docs` this way (rust-embed of `../../docs`).

Markers live at `s3://<sccache bucket>/ci-pass/<repo>/<job>/crate/<name>/<hash>`, body = the commit sha. All lookups run in one pass (parallel `curl --aws-sigv4`). As with the whole-repo cache, `build` skips a crate only when both its `build` and `test` markers exist, so the nextest archive always contains every crate `test` runs. Any backend failure (no endpoint/keys, network error, a reply other than 200/404, a missing result) reports every crate as needing work, never a false hit. An empty or malformed `hashes` input fails `check-batch`; `record-batch` warns and records nothing. Force a full run with `workflow_dispatch` and `force: true`; orca's nightly schedule forces one. S3 credentials reach curl through a mode-600 `--config` file, never argv.

### Container images: built on main, promoted by release

A repo with a `Dockerfile` copies `templates/plugin-image.yml` to `.github/workflows/image.yml`; repos without one leave it out. That `Image` workflow runs on every push to `main` (and on `workflow_dispatch`), never on PRs. Its `image-build` step tags the image by the commit's tree sha, `<registry>/argyle-labs/<repo>:tree-<sha>` from `git rev-parse HEAD^{tree}`, with the name lowercased. If that tag already exists the build is skipped. Otherwise the image is built, pushed, and the registry build cache at `:buildcache` is written.

Release never builds an image. A caller passing `image_name` to `plugin-release.yml` gets a `Promote image` step in the `release` job. It runs only after every requested build job has passed, and before the release is published. `image-promote` polls for `:tree-<sha>` of the release commit for up to `image_wait_minutes` (default 15), so a release dispatched right after a merge waits for the `Image` run. It then retags registry-side with `docker buildx imagetools create`, so every platform is kept: `<version>`, plus `latest` for stable or `rc` for rc. If the image is still missing at the deadline, the release fails before anything is published. Both actions treat only a "not found" reply from `imagetools inspect` as missing. Any other error, such as auth or network, fails with its own message.

PR validation is opt-in. Both `plugin-ci-rust*.yml` templates end with a commented `image-check` job. When enabled, it builds the Dockerfile with `push: false`, reads `:buildcache`, and never writes the cache or pushes.

Registries: Gitea (`gitea.scottkey.me`) is the primary, private registry and holds every tag, including `tree-*`. `ghcr.io/argyle-labs/<repo>` is the public mirror of release tags only. After a successful promote, the `release` job copies `<version>` and `latest`/`rc` from Gitea to ghcr.io with `docker buildx imagetools create`, so the manifest list (every platform) is copied and nothing is rebuilt. It logs in with `secrets.GH_TOKEN`. A failed mirror emits a warning and a step-summary line, and the release still succeeds. Pass `image_public: false` to opt out. Public docs on GitHub reference `ghcr.io` images; internal compose files and hosts pull from Gitea.

Multi-arch images can also be built from the release itself, after `publish`: a `build-image` matrix job per platform (each on a runner of that arch) calls `job-image-build-platform` with `ref: ${{ needs.version.outputs.tag }}`, so it builds exactly the tagged commit and pushes by digest; an `image` job (`needs: build-image`) calls `job-image-merge` with `tags:` set to the version plus `latest` for stable or `rc` for rc. Running after `publish` keeps a failed image build from blocking the release.

```yaml
build-image:
  needs: [version, publish]
  strategy:
    matrix:
      include:
        - { platform: linux/amd64, runner: ubuntu-latest }
        - { platform: linux/arm64, runner: arm64 }
  runs-on: ${{ matrix.runner }}
  steps:
    - uses: argyle-labs/.github/.github/actions/job-image-build-platform@main
      with:
        ref: ${{ needs.version.outputs.tag }}
        image: argyle-labs/${{ github.event.repository.name }}
        platform: ${{ matrix.platform }}
        username: ${{ secrets.CI_REGISTRY_USER }}
        password: ${{ secrets.CI_REGISTRY_TOKEN }}
image:
  needs: [version, build-image]
  runs-on: ubuntu-latest
  steps:
    - uses: argyle-labs/.github/.github/actions/job-image-merge@main
      with:
        image: argyle-labs/${{ github.event.repository.name }}
        tags: |
          ${{ needs.version.outputs.version }}
          ${{ needs.version.outputs.prerelease == 'true' && 'rc' || 'latest' }}
        username: ${{ secrets.CI_REGISTRY_USER }}
        password: ${{ secrets.CI_REGISTRY_TOKEN }}
```

`registry-login` holds the shared Buildx setup (including the plain-HTTP buildkitd config) and the registry login that both image actions use. Pass `setup-buildx: 'false'` to log in to a second registry (ghcr.io) on top of an earlier login.

### Adding a tool step

Add `- name: <Tool>` / `uses: argyle-labs/.github/.github/actions/<tool>@main` to the job action (or orca job) of the check it belongs to, with `if: ${{ !cancelled() }}` when it is not the first tool step, and `with:` for any inputs. No other wiring. Node tools each run `npm ci` unless `install: 'false'`; set that on every node step after the first in a job.

### Job setup: `rust-setup`

Composite actions cannot read `secrets`, so credentials come in as inputs set from `secrets.*` by the caller. `rust-setup` runs once per job and owns the job-wide cargo environment: `sccache-endpoint` (`vars.SCCACHE_ENDPOINT`), `sccache-access-key` / `sccache-secret-key` (`secrets.SCCACHE_S3_ACCESS_KEY` / `secrets.SCCACHE_S3_SECRET_KEY`), `wrap-cc: 'true'`, `build-jobs`, `debuginfo` (default `'0'`), `env` (extra `KEY=VALUE` lines exported for the job; trusted input, it can set any variable, so it must come from the repo's own workflow file and never from event data), `orca-fetch-token`, `working-directory`, and `drop-cargo-config` (default `'true'`: deletes `.cargo/config.toml`, where plugins keep a local-dev path patch; orca passes `'false'` because its committed config carries `LIBSQLITE3_FLAGS`).

### Action catalogue

Common inputs: `working-directory` (default `.`) on every action; `artifacts` (lines of `name:path`, at most 4, downloaded by name before the tool runs) on every action that compiles or builds. Cargo `args` are split on whitespace with no quoting: pass features comma-separated, e.g. `--features a,b`. Node `command` overrides the tool invocation (e.g. an npm script); it is `eval`ed, so it is trusted input only, from the repo's own workflow file.

| Action | Runs | Extra inputs | Outputs |
|---|---|---|---|
| `cargo-build` | `cargo llvm-cov nextest-archive` (the build: test binaries, compiled once, coverage-instrumented; plain `cargo nextest archive` when `coverage: 'false'`) | `args`, `coverage` (default `'true'`), `name-suffix` | artifact `nextest-archive<name-suffix>` |
| `cargo-test` | the archive, once, via `cargo-llvm-cov` (plain `cargo nextest run` when `coverage: 'false'`); then `cargo test --doc` unless `doctests: 'false'` | `args`, `coverage` (default `'true'`), `nextest-args`, `doctests` (default `'true'`), `name-suffix` | artifact `lcov<name-suffix>`, step-summary table |
| `cargo-clippy` | `cargo clippy -- -D warnings` (also compiles bins/examples) | `args` | |
| `cargo-fmt` | `cargo fmt --all --check` | | |
| `cargo-lock-check` | Cargo.lock drift (path-patch entries, out of sync) | `mode`: `enforce` \| `warn` | |
| `cargo-llvm-cov` | how `cargo-test` runs with coverage: the archive under `cargo llvm-cov nextest --no-report`, then a report-only lcov/summary | `nextest-args`, `name-suffix` | artifact `lcov<name-suffix>`, step-summary table |
| `vite-build` | `npx vite build` | `command`, `install`, `dir` (default `dist`), `artifact-name` (default `vite-dist`) | artifact of `dir` |
| `svelte-check` | `npx svelte-check` (type check) | `command`, `install` | |
| `tsc` | `npx tsc --noEmit` (type check) | `command`, `install` | |

| `eslint` | `npx eslint .` (lint) | `command`, `install` | |
| `prettier` | `npx prettier --check .` (format) | `command`, `install` | |

| `actionlint` | actionlint over the repo's workflows | `version` | |

Shared plumbing under `.github/actions/`: `rust-setup` (above), `fetch-artifacts` (the `artifacts` handoff), `node-install` (`npm ci` with npm cache), `ci-summary` (phase timings, sccache stats), `source-hash`, `crate-hashes` and `ci-pass-cache` (the pass caches above), `registry-login`, `image-build` and `image-promote` (container images, above).
